# Eight-upload server timing and stepped authenticated-session pilot

**PREPARED, NOT EXECUTED.** This strictly bounded one-shot workflow exercises the existing eight approved synthetic Student identities (with temporary private reviewer aliases enabled only for this test) on the Render Free staging service, and no other academic records. Eight new synthetic projects with their own teams are created to ensure that legitimate fresh PDF uploads and submissions are measured without attempting to reopen historical released projects. Exactly eight simultaneous 128 KiB PDF uploads are SHA-256 checked against the private storage readback and submitted once each; retained history is validated.

The server's existing `SMARTPRO_UPLOAD_TIMINGS=YES` switch records only numerical substep durations for parsing, PDF validation, SQL PREPARE, SQL START, S3 private storage and COMPLETE; this does not log PDF bytes or credentials. The same unchanged 5.000-second *eight-client p95* upload target that was missed by 5.059 seconds remains enforced. Each of eight client-side wall times is printed for comparison, without identifying users.

After writes, the pilot creates 16 additional independently authenticated *sessions* mapped to the same eight synthetic Student UUIDs and performs 30 two-second-spaced waves: 10 waves × 8 sessions, 10 × 16 and 10 × 24 = **480 read requests total** (up to 24 concurrent at peak). It verifies each extra session maps to the expected Student identity and each request is authorized HTTP 200; stops on multiple delays over five seconds or unexpected HTTP failures. It records p95/max by concurrency tier and preserves the previously defined 2.0-second pooled read p95 goal. The profile is **eight different Students and up to 24 sessions, not 24 different students**. This cannot certify dozens/hundreds of independently authenticated simultaneous students or any campus-wide SLA.

Uses no paid services, free trials, stress ramp, extra database privileges, S3 public access or automatic retry. No credentials or document contents in code/artifacts. A measured p95 exceeding either objective is a real test performance miss, even if all academic writes/reads succeed; do not weaken thresholds or replay merely to seek a passing sample. After the test, disable the temporary Render login aliases and upload timing logs again.

Historical reason: [earlier eight-student run #43189485424](https://github.com/10Stardust01/Smart-Pro/actions/runs/43189485424) completed all academic integrity and 480 read checks but had eight-upload p95 **5.059 s** versus unchanged objective **5.000 s**. The earlier run lacked server substep traces, so client latency alone did not identify a bottleneck.
