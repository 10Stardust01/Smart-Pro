# SMART-PRO — signed scoped read soak, mobile accessibility, and human acceptance

**Status: PREPARED, NOT YET EXECUTED.** The one-shot workflow is triggered once by landing its own new workflow file on `main`. It performs **no academic writes**, file downloads or login creation, and uses the existing five synthetic reviewer sessions. Free Chromium/HTTP libraries and existing included Actions minutes only; no trials, paid upgrades, TinyFish, or GitHub request floods.

## Actual-hosted scoped-read soak

60 waves, once every 2s at most; five verified role identities (Student, Faculty, Coordinator, HOD, Admin), at most **five GETs at a time, 300 GETs total** following a sequential login/read-only authorization preflight. Actual endpoints alternate between Student project/document pages, Faculty scoped document page, Coordinator bounded offering/evaluation queue, HOD document page and Admin leadership/workspace. Unavailable or unauthorized scoped endpoints stop the test rather than silently substituting cheaper generic requests. Reports p50/p95/p99, per-role and per-scoped-route p95, errors and bounded 5s stop gate. Provisional goal is pooled read p95 ≤2s, separate from operational stop gate and Render Free cold-start warming. It is a *profile-specific* response-time pilot, **NOT** evidence of 16 separately signed-in students or sustained deadline-time writes. Earlier [mixed academic write pilot](https://github.com/10Stardust01/Smart-Pro/actions/runs/43132925649) remains complete and is not repeated.

## Actual-hosted mobile accessibility

Actual signed-in Chromium with viewport width 320 CSS pixels, five roles/ten screens; checks for accessible main/nav, labeled visible inputs, at most 16px of global horizontal overflow, keyboard-focusable navigation, and native required-field focus on empty reviewer login. No invalid login POST and no academic commands. This checks narrower UI/reflow than earlier five-role ten-screen zero-axe report [#43138537587](https://github.com/10Stardust01/Smart-Pro/actions/runs/43138537587). A red run means a reportable responsive defect; never conceal it by widening the tested viewport or claiming mobile acceptance.

## Human assistive-technology acceptance — requires a person

This is a **manual check**, not something browser automation can establish by inspecting ARIA attributes. An actual human reviewer using their own authorized synthetic account should perform at least: (1) in Windows NVDA or built-in Narrator, traverse headings, landmarks and keyboard-only navigation; (2) review a Student project, upload control, submission history, validation error and current result; (3) with Faculty/Coordinator access, read evaluator queue status, assessment labels and publication confirmation without making an unplanned change; (4) test TalkBack on an Android browser or VoiceOver on iOS Safari for focus order, announced buttons and dialogs; (5) increase text to 200%, verify no hidden controls/scroll traps, and return focus after dialogs. Record each role, assistive technology and version, device/browser, URL/view, observed speech/behavior, and pass/fail with screenshot/description, without screenshots of confidential grades or credentials.

**Existing original private PDFs:** 41/41 contained extractable text, but **39/41 lacked structure tags**. This cannot be made acceptable merely by changing the preview image. Keep original immutable academic evidence; create an accessible companion or obtain a properly structured replacement under **explicit authorized academic versioning**, not a silent overwrite or invented mandatory document policy. A human must check heading/table order and reading sequence in a sample of the actual accessible companions before PDF accessibility acceptance is marked passed.

## Distinct-student hosted write capacity — separate setup, not silently waived

Existing supplemental reviewer aliases can reuse **the same underlying student actor UUID**. The 16-actor PostgreSQL test passed in an isolated environment but did **not** test 16 signed-in hosted student accounts. A valid next hosted write run requires separately provisioned approved **synthetic student actor UUIDs**, independent restricted student role scope, isolated test teams/projects, and independent **signed reviewer credentials configured in both Render and GitHub encrypted secrets**. No auth bypass, public static passwords, reusing one student's session or overwriting existing reviewer test account settings. Restore/revoke the temporary credentials after a bounded validated test while retaining audited academic history. Stop until that private staging setup is ready; no paid or free-trial services are needed.
