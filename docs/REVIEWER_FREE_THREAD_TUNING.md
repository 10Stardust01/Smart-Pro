# SMART-PRO Render Free bounded request-thread experiment

**Status after tests (12 November 2026):** The bounded four-thread baseline remained functionally correct but missed the 5-second upload target (p95 5.641s); eight-thread staging test also completed eight uploads/submissions correctly but worsened p95 to 6.126s and stopped at the first non-200 response during 16-session reads. This is a **measured performance nonpass**; the original target has not been changed. The eight-thread setting was reverted to four and staging logins/timing diagnostics were disabled, confirmed Live. See [run #43195738956](https://github.com/10Stardust01/Smart-Pro/actions/runs/43195738956) and [run #43197635174](https://github.com/10Stardust01/Smart-Pro/actions/runs/43197635174). All 8+8 fresh synthetic version uploads were SHA256-checked; no new teams/projects. Free-tier capacity is not established beyond the bounded read pilot.

**Baseline observed on 12 November 2026, before this change:** [Eight-upload and stepped read run #43195738956](https://github.com/10Stardust01/Smart-Pro/actions/runs/43195738956), using **one Gunicorn worker and four gthread request threads**, verified 8/8 original private PDF uploads, 8/8 submissions (p95 1.111s) and 480/480 signed reads. Eight concurrent 128 KiB PDF upload p95 was **5.641s**, missing the original **5.000s** goal; 8/16/24 concurrent signed-session read p95 was **0.891s / 1.330s / 1.963s**, pooled **1.882s** (goal 2.000s). This is eight genuine Student identities with up to 24 sessions, not 24 separate Student actors.

A dedicated server timing run captured eight `smartpro_upload_timing` records: S3 write time ranged **65.8–3572.7ms**, PDF verification **246.4–402.4ms**, and COMPLETE SQL **10.4–101.2ms**. First four private-storage calls were about **2.8–3.6s**, the other four **0.07–0.11s**. This is consistent with storage stalls and queueing under four request threads but is not proof of the exact network cause; do not claim that increasing threads eliminates remote S3 latency.

The Dockerfile now permits only `SMARTPRO_GUNICORN_THREADS=4`, `6` or `8`; **unset defaults to the same original four**. One worker is retained. Only the existing isolated Render Free reviewer staging deployment should be configured with `SMARTPRO_GUNICORN_THREADS=8` for one controlled follow-up. All other environments remain at their original four threads, so this is not an unmeasured global rollout.

**Acceptance:** Retain unchanged eight simultaneous 128KiB PDF upload p95 objective **5.000s**, Student submission p95 **3.000s**, and pooled signed read p95 **2.000s**. Report server S3/SQL/PDF validation substeps separately from client elapsed times. A fresh synthetic Student upload is permitted only after an assigned Guide, under their already authorized role, requests a second revision on the eight existing, clearly synthetic projects. **No new teams or projects**, no paid services, no trials, no uncontrolled flood, no anonymous traffic, no relaxation of thresholds and no automatic retries.

**Rollback:** Set staging `SMARTPRO_GUNICORN_THREADS` back to `4` (or unset it), and `SMARTPRO_UPLOAD_TIMINGS` to empty after the measurement; Render environment updates redeploy this Free reviewer service. Remove the eight temporary reviewer load aliases afterward, leaving immutable synthetic project history. Do not run a new academically significant write wave merely to fish for a passing p95.
